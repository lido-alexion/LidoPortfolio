## 5. V1 vs V2 maturity comparison

V2 introduced a repeatable discipline: **SPEC → BOUNDARY → POLICY → GAP → delivery/reconciliation**. Most V1 surfaces pre-date that and rely on architecture intent + `implementation.md` + scattered tests.

| Discipline | Typical V2 (F042…F144) | Typical V1 core | Gap |
|------------|------------------------|-----------------|-----|
| Specification (CURRENT vs TARGET) | Pack SPEC | Arch SHALL docs (often aspirational) | V1 code vs SHALL drift common |
| Boundary definition | Explicit BOUNDARY.md | Implicit / SD-xxx only | Ownership fights (cash vs ledger vs recs) |
| Policy decisions register | POLICY-DECISIONS.md closed | Chat + SD + backlog | Hard to know “DECIDED” |
| Acceptance criteria | Testable ACs in pack | Demo checklist / partial tests | Uneven |
| Regression audit / final compliance | FINAL audit or COMPLETE_WITH_NON_BLOCKERS | 2026-07 MVP audit + feature coverage | Stale relative to post-V2 product |
| Help sync | Enforced by delivery + F143 | Present but drift-prone | Medium |
| Automated tests | Initiative-gated | Large but uneven; some risky/failing | Analytics/cash weak spots |

**Highest maturity debt (V1):** Cash, Dashboard/Explorer analytics, Discovery/Evaluation (no Discovery Engine SPEC), Strategy↔Evaluation parameter wiring, Universe sync ops, Snapshots (F015) vs Historical Holdings (F014).

**Highest maturity (already V2-grade):** F042/F043, F127, F019/F014, F060, F137, F003/F005, F143/F144.
