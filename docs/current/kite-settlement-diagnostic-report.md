# Kite settlement readiness diagnostics

The `GET /api/kite/settlement-readiness` route is wired to `KiteSettlementReadinessController` and `KiteSettlementDiagnosticReport`. It returns a read-only, bounded diagnostic for one StoX profile, the authenticated user's connected Kite account, and one date. It reads existing portfolio snapshots, CNC imports and sync runs, and account-scoped funds snapshots. It does not call Kite, persist results, change reconciliation or transactions, send notifications, or gate execution. It is not the reconciliation UI and does not establish that brokerage settlement matched StoX.

## Route access and request semantics

- The route uses the API's authenticated-user middleware and additionally requires `token.scope:portfolio:read`. It removes `ResolveActivePortfolio` middleware and resolves a profile itself: `X-Profile-Id`, then `X-Portfolio-Id`, then `portfolio_id` query parameter; if none is provided it selects the authenticated user's default profile. A supplied profile must be a scalar numeric ID owned by that user; otherwise the route returns not found.
- The route never accepts an account ID from request input. It selects the authenticated user's Kite connection, requires exactly one, requires usable credentials plus non-null `connected_at` and a future `expires_at`, and takes the account ID from that connection's `broker_user_id`. Missing, stale, expired, ambiguous, or malformed account identity returns conflict. The response may include account identity; treat it as sensitive.
- `date` is optional and must be an exact valid `YYYY-MM-DD` no later than today in `Asia/Kolkata` and no earlier than one year before today in `Asia/Kolkata`. If omitted, today in that timezone is used. CNC execution bounds are IST midnight inclusive to next IST midnight exclusive, converted to UTC for the database query. Diagnostic timestamps are assigned to a day after conversion to `Asia/Kolkata`; malformed or out-of-scope timestamps do not qualify. Snapshot and trading-date fields must exactly equal the requested valid date.
- Each source query is scoped to the resolved profile and/or connected account where those columns exist. Each result list is limited to 5,001 rows so the route can reject a volume over 5,000 with 422. Invalid date input returns 422; unauthenticated access returns 401; inaccessible profile returns 404. Diagnostic counts are scoped observations, not completeness assertions.

## What the stored evidence means

- `portfolio_portfolio_snapshots` now stores `profile_id` and `snapshot_date` (the legacy `user_id` schema was migrated). It has no Kite account ID: a row is a profile-level portfolio snapshot, not a Kite holdings snapshot or account settlement proof.
- `kite_cnc_trade_imports` has profile, execution, instrument, status, broker trade/order, and nullable `broker_account_id` provenance fields. Rows with an explicit foreign account are excluded. Legacy rows with no account remain visible only as `legacy_unbound_count`, not account evidence. Even explicit-account rows in this diagnostic are described as profile-attributed; import/review status and missing historical attribution remain limitations. The source table does not provide a complete historical-account coverage record.
- CNC rows are selected for the requested IST execution day. The route selects runs by profile, connected broker account and date and complete only when the newest run by `started_at` has status `completed`, a valid completion time, and zero reviews; malformed run timestamps fail closed. A failed latest run cannot inherit completion from an older successful run.
- Funds snapshots store profile, account, trading date, capture time, freshness, balances and payout-semantics metadata. The route excludes other accounts. Funds values are aggregate cash observations, not holdings or settlement proof; stale or uncertain freshness and unverified payout semantics remain diagnostic warnings.
- There is no durable, independently account-attributed daily Kite holdings/positions capture wired into this route, and the controller supplies neither StoX holdings nor a broker snapshot to the classifier. Therefore `holdings_diagnostic` is null and no settlement comparison is performed by the route.

The pure `KiteSettlementEvidencePreparation` adapter can validate an already supplied candidate snapshot and locally persisted trade rows, but it makes no provider request and does not authenticate an account. Its structured `source_proof` receipt is caller-supplied lineage metadata: Kite provider/account/capture ID/time and successful requested `holdings` and `positions` results. Shape validation does not independently verify that Kite returned those values. Its completeness flags describe validated input shape and scope only. For trade completeness it additionally requires explicit profile and broker-user provenance, accepted statuses (`imported`, `matched_manual`, `matched_existing`), unique valid broker trade IDs, and an explicit complete `persisted_historical_imports` coverage record with `from`, `through` equal to the as-of date, and the active account identity. A current-day Trades API response is not historical coverage. The durable CNC import schema stores a nullable `broker_account_id`, not the adapter’s `broker_user_id` field. An explicit, trusted mapping would be needed; account provenance cannot be assumed from profile ownership.

The shadow holdings classifier treats holdings, positions and trades as distinct inputs. It does not add positions to holdings. A possible pending-settlement explanation is only `pending_settlement_exact_evidence` when complete trade evidence exactly explains a quantity gap without overlapping position evidence or opposing active trade sides; it remains `review_required`, not a settlement match. `evidence_consistent` is a classifier status for supplied shadow evidence only, not proof of brokerage settlement. Cash stays separately classified as `unknown_non_comparable_broker_funds` unless explicitly marked comparable; this adapter always marks it non-comparable.

## Response status vocabulary

- Top-level `diagnostic_only_review_required` is fixed: this endpoint never declares acceptance or settlement match. The `claim` explicitly says no actual brokerage settlement match is asserted, and `independent_settlement_data_available` is false.
- `account_binding` is `verified_explicit_mapping` only when profile/account mapping is established from durable account-scoped CNC run/import or funds rows; otherwise it is `unverified`. This is application provenance, not independent brokerage verification.
- Evidence `count` values mean rows survived the profile/account/day filters. Related diagnostics identify missing snapshots/imports/runs/funds, unbound legacy trades, foreign-account exclusions, incomplete sync, stale funds, missing holdings sources and absent independent settlement confirmation. They do not mean all relevant history or brokerage data is present.
- If a separately invoked shadow comparison exists in future, its nested `review_required`/`evidence_consistent` status and row states describe only supplied evidence. `pending_settlement_exact_evidence` is an exact candidate explanation, not confirmed settlement; `unresolved` requires review. None changes the route's top-level status or operational state.

## Operator evidence checklist

Use only evidence already available to an authorized operator in Zerodha Kite, Console and StoX. Do not share access tokens, session cookies, client secrets, full account numbers, or unredacted personal/bank details. Keep original exports/screenshots in approved restricted storage; when discussing findings, use a masked account label and redact unrelated rows while preserving date, status, instrument, quantity and relevant totals.

For a controlled evidence review, record the IST as-of date, masked Kite account label, StoX profile label, capture times/timezone, source screen/report name, and whether the source is a direct Console statement or a StoX/local receipt. Compare like-for-like periods and include:

1. **Broker holdings:** the actual account's holdings statement/export for the as-of date, including symbol/ISIN, exchange, quantity, T1 quantity, used quantity and capture time where available. Record unavailable fields as unknown; do not assume Console provides the API field names. Preserve an explicit empty result if the account held nothing.
2. **Broker positions:** net and day positions for the same account and date, including explicit empty buckets. Determine from real examples whether positions overlap holdings or fills; do not sum them into holdings.
3. **Console trades and history:** executed CNC fills with trade IDs, execution timestamps, side, quantity, product and instrument. Record the historical export's covered-from/through dates and any gaps, account identity, and whether it is an actual Console tradebook/statement. A current-day Trades view, local sync receipt, imported row or profile-level transaction is not historical coverage or independent settlement confirmation.
4. **Independent settlement evidence:** obtain the relevant official contract note/settlement statement or other brokerage settlement confirmation for the same account, dates and fills. Reconcile charges and settlement/reflection outcomes to these records; a local source-proof receipt, API-shaped payload, sync status, funds snapshot or matching quantity alone is not independent proof.
5. **StoX comparison inputs:** establish the trusted profile holdings source and identify which transactions have broker trade IDs and explicit account provenance. Classify manual, unmatched, legacy/unbound and review-only rows separately; do not treat them as verified broker fills. Preserve missing or unavailable sources as unknown rather than zero.
6. **Cash separately:** compare Console ledger/statement evidence for pay-ins, payouts, charges and balances with StoX cash records. Aggregate buying power and funds snapshots do not prove individual transfers, fees or holdings settlement; payout field semantics remain unverified until checked against Console examples.

An evidence packet should contain masked references or restricted-storage paths, period coverage, source and capture metadata, exceptions, and reviewer conclusions. Do not paste raw credentials or full broker payloads into tickets or this report. No Console evidence is assumed to exist or to have been reviewed by this document.

## Missing before settlement-aware reconciliation or selector removal

The route currently supplies no durable account-labelled daily holdings/positions observations, and the import schema has nullable account labels rather than independently verified per-trade identity, and lacks authoritative historical coverage. A caller-supplied capture receipt cannot fill either gap. Before a separate settlement-aware integration can be accepted, it needs durable profile/account/date/capture provenance for observations and independently reviewed Console/statement examples establishing real holdings, T1/used, positions overlap, trade reflection, and session/settlement dates. It also needs complete account-bound historical CNC coverage, row-level reflection handling for partial or mixed-side fills, explicit unknown/missing-source handling, and evidence for cash, charges and payout semantics kept outside the holdings comparison.

The frozen CNC product decision keeps the include-today/exclude-today selector until a replacement is implemented and validated. Evidence must show representative live-account outcomes without double-counting same-day or prior unsettled trades, weekend/holiday/special-session behavior, positions overlap and unresolved cases, and safe reviewed results over existing discrepancies. Only then can a separate implementation and acceptance decision remove the selector. This diagnostic route does not constitute that implementation or acceptance.
