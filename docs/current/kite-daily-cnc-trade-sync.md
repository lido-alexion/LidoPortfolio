# Kite daily CNC trade sync and reconciliation

StoX imports executed NSE/BSE equity trades with Kite product `CNC`. Other products and derivatives are excluded. Each fill is written through `TransactionWriteService`, reusing the existing fees, holdings, realization, and cash ledger behavior. Import records are unique by profile and broker trade ID, and retain broker order/trade IDs, execution data, and broker evidence. Each run and import records the connected Kite `broker_user_id`; a changed account or legacy unbound import pauses sync instead of combining account histories.

The scheduled command runs after market close plus the configured reconciliation delay (30 minutes by default). A successful Kite reconnect attempts current-day catch-up, and users can trigger a manual sync from the reconciliation card. Kite's Trades API exposes the current day's trades only, so missing sessions are recorded as unavailable gaps when there is a prior successful sync to establish the interval. Repeated runs are idempotent.

Existing transactions are matched by stock, side, date, quantity, and exact execution price. A unique manual match links to the existing transaction. Transactions already linked to a broker import are excluded from reuse, and a late manual transaction that could overlap previously imported fills keeps new fills in review without another ledger write. Ambiguous matches remain in review. Unmatched trades use the common transaction write path; an account linked to multiple eligible live portfolios is paused for ownership review to avoid duplicating one broker execution across portfolios.

Kite `GET /trades` represents each partial fill as an individual trade. Its `average_price` is the execution price for that filled quantity, and `fill_timestamp` is the exchange fill time. CNC imports use those fields as canonical execution price/time. An optional legacy `price` is accepted only when `average_price` is absent; when both occur they must be positive and agree. Missing, malformed, or conflicting prices stay in review. Neither `exchange_timestamp` (exchange order registration) nor `order_timestamp` substitutes for missing fill time.

Reconciliation uses persisted CNC fill evidence only for a settlement adjustment when its complete net quantity exactly explains the difference between StoX and the normalized Kite holdings quantity (`quantity + t1_quantity - used_quantity`). Partial or ambiguous reflection remains a discrepancy. The existing include/exclude-today selector remains available while this behavior is validated. No funds or order-execution baseline policy is changed by this slice.

Kite's available equity buying power is retained as broker evidence but is not treated as comparable accounting cash. Such a snapshot reports funds as `unknown`, even when the numeric amount happens to equal StoX cash. The existing per-order safeguards and reconciliation blocking behavior remain unchanged. This feature does not create automatic bank adjustments.

The reconciliation dashboard lists the active portfolio's latest CNC sync runs by trading date, with trigger (scheduled, reconnect, manual, or gap detection), last-run time, imported and matched counts, review counts, and safe failure or historical-unavailable summaries. It refreshes while open. The API response is scoped to the active portfolio and exposes run summaries only; raw exception text, broker row evidence, and credentials are not included in this activity list. Historical gaps remain unresolved because Kite's Trades API cannot retrieve arbitrary past sessions.

`manual_match_review` and malformed CNC candidates are persisted as row-level review evidence, including CNC rows with missing or invalid exchange, side, time, symbol mapping, or fill values. The review list/detail/actions are scoped to the active portfolio and connected Kite account, while legacy accountless rows remain visible only as unresolved profile history. New fills continue to sync when unrelated legacy rows exist. If a current account trade ID collides with an accountless legacy row, the old row stays unresolved and the current fill is saved separately as an `account_conflict` review item without a ledger write. Stored and returned evidence uses bounded, validated execution fields; duplicate rows retain at most eight sanitized variants and trade responses are capped at 5,000 rows and 5 MB per sync. Provider payloads, instrument tokens, credentials, personal details and error bodies are not exposed by the review API or stored sync failure summaries. Replays deduplicate by broker trade ID when available and by a stable evidence fingerprint when it is absent. A later well-formed replay enriches an earlier malformed candidate but keeps it in review and does not import it automatically. Legacy rows keep their existing transaction links and are never rebound to the current account automatically.

The post-cutoff scheduler stops after a scheduled run completes or reaches `needs_review`. Failed runs retry on later scheduler ticks. An explicit `/trades` HTTP 401/403 is recorded as the fixed `kite_trades_auth_rejected` category and displayed with guidance to check the Kite connection or account permissions; this does not establish token expiry, invalidate a session, or retain provider response text. Repeated scheduled attempts for this category are limited to one per hour, scoped to the same profile, connected broker account, and trading date. The retry resumes after the cooldown, while manual and reconnect catch-up remain available immediately. Other failures retain generic summaries and their existing retry behavior. A later same-day manual sync can replay the current-day tradebook and enrich a now-valid malformed candidate, but it remains `manual_match_review` and never posts automatically. Once the current-day tradebook is unavailable, unresolved candidates need independent broker evidence and operator review; no old price or execution time is inferred.

The legacy authenticated `/api` contract exposes `GET /reconciliation/trades/review` (optional `status`, `trading_date`, `per_page` filters), `GET /reconciliation/trades/review/{item}` (sanitized evidence and exact unlinked candidates), and `POST /reconciliation/trades/review/{item}/resolve`. Mutations require `action` (`acknowledge_unresolved` or `match_existing`), a 16–80 character alphanumeric/underscore/hyphen `idempotency_key`, and the displayed 64-character `evidence_key`; matching also requires `transaction_id`. Audits store a fingerprint of the idempotency key, the evidence fingerprint, actor, action, result and idempotency request hash. Reusing an idempotency key for a different request returns 409, as does stale evidence, a duplicate acknowledgment or a transaction that no longer exactly matches. These are legacy `/api` endpoints, outside the generated `/api/v1` OpenAPI document.

An operator may record an idempotent audited acknowledgment, which explicitly leaves the item unresolved, or link a complete execution to an already-booked transaction after exact profile, stock, side, execution date, quantity and price checks. The link action locks both records and rejects a transaction already linked to another execution. Neither action creates or edits a transaction. Automatic/manual matching also requires exact price equality; near matches remain review items. There is deliberately no manual transaction import from the review workflow: incomplete/ambiguous evidence cannot safely provide authoritative transaction details, fees, or proof against already-booked cash and holdings. Historical API gaps remain unresolved and require independent broker tradebook evidence; row acknowledgment does not resolve those gaps or promote a run to reconciled.
