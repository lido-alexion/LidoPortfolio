## Implemented path

Factor metadata stores version, row count, and hashes of both images. Capture, adjustment, snapshot completion, and the completed marker share the stock-locked repair transaction.

Admin endpoint `POST /api/data-quality/issues/{issue}/rollback-completed-repair` restores those before-images by primary key and appends a linked rejected resolution in one transaction. It verifies snapshot integrity, exact row membership, and every current after-image hash before writing. It refuses legacy completed factors without snapshots, incomplete images, drift, and overlapping factor/F020 events. Raw evidence and unrelated price rows remain untouched; the factor is deactivated and rollback metadata is retained. Repeating a successful rollback is idempotent. The existing accept/reject guard still blocks metadata-only reversal while repair is completed. Derived metrics and repair proofs refresh; Strategy/ML/trading replay is not invoked.

## Post-approval automation safety gate

Approval deliberately stages a pending F042 factor and does not enqueue or call OHLCV repair. No unattended post-approval writer is enabled. The existing transactional row snapshots support audited exact rollback, but they are stored in the same application database as the rows they protect; they do not establish that an independent backup exists or can be restored. An offline verifier now checks a custodian-signed receipt, backup and restore-report SHA-256 digests, isolated full-restore assertions, and the exact factor/preflight/row fingerprint. No receipt producer, trusted custodian key, actual isolated restore proof, or rollout authorization is present here, so the required pre-apply recovery condition remains unproven. This verifier does not connect to a database and does not authorize or invoke repair.

The signed receipt format is `stox-f042-backup-restore-proof-v1` JSON. It binds positive `factor_id` and `stock_id`, `preflight_sha256`, `protected_rows_sha256`, backup path/hash/creation time, source database identity, restore-report path/hash, a distinct restored database identity, restore completion time, `restore_status: passed`, `full_restore: true`, and `isolated_restore: true`. The dry-run prints both the overall preflight digest and the protected-row image digest. The detached signature is raw OpenSSL SHA-256 signature bytes over the exact receipt file bytes. Backup, report, receipt, signature, and custodian public key must be held outside the application database; the trusted public key must be provisioned through an independently controlled release configuration. Verify with `php scripts/verify-f042-backup-proof.php RECEIPT.json RECEIPT.sig TRUSTED_PUBLIC_KEY.pem FACTOR_ID STOCK_ID PREFLIGHT_SHA256 PROTECTED_ROWS_SHA256`, supplying the independent values copied from the exact dry-run. A PASS establishes integrity and custodian attestation for the supplied artifacts, not that the source was production or that a future apply is authorized. The receipt must be generated from a disposable native MariaDB restore rehearsal of the exact preflight-bound database backup, and its protected-row digest must match the F042 preflight. No automatic writer should consume the receipt until the real backup producer, custodian-key governance, isolated restore process, and explicit rollout are accepted and rehearsed.

The nonproduction preflight contract is the exact-factor dry-run: select one factor ID with `portfolio:repair-corporate-action-prices --factors-only --stock=<stock-id> --factor=<factor-id>`, omit `--apply`, and preserve the returned stock, issue, action type, ex-date, stored divisors, row count, affected range, samples, protected-row image digest, and `preflight_sha256`. The fingerprint covers all raw factor attributes, all raw linked issue and latest resolution attributes, and the complete ordered physical price-row image before the ex-date. It is read-only. To require that exact preview during a later explicit apply, pass `--apply --factors-only --stock=<stock-id> --factor=<factor-id> --expected-preflight-sha256=<sha256>`. Under the issue → stock → factor lock order, apply locks the linked approval/resolution and affected price rows before rechecking the fingerprint, eligibility, linked approval, and duplicate ownership. Linked newly approved factors must match the divisor formula for their accepted ratio; unlinked legacy factors require explicit `divisor_provenance: legacy_stored_factors` to retain stored-divisor behavior. Any mismatch fails closed and requires a new review. This implements preflight-to-apply revalidation for a single factor; it does not supply the missing independent backup proof or enable unattended apply.

Any future automatic pathway must remain disabled until all of these controls are independently demonstrated: (1) a durable backup receipt for the affected database state from outside that database, verified by an isolated restore rehearsal before enqueue; (2) an exact factor and complete affected-row fingerprint bound to approval and preflight; (3) a second fingerprint and approval/ownership check under the issue → stock → factor lock order immediately before mutation, aborting on any difference; (4) atomic before/after evidence, completion state, and derived-data work with exact rollback that refuses row-set or content drift; and (5) a durable one-factor execution claim that serializes F020/F042 writers, prevents duplicate workers, and sends ambiguous outcomes to human review instead of automatic replay. The current same-database snapshots, dry-run output, transaction, and row locks do not prove the external backup/recovery and durable dispatch contract. Do not add a queue dispatch from approval or enable a scheduler/worker until these conditions are implemented and rehearsed on disposable native MariaDB.
