# Kite settlement evidence preparation adapter

`KiteSettlementEvidencePreparation` is an isolated pure mapper for synthetic or already retrieved evidence supplied to the shadow comparator. It performs no provider calls, database writes, portfolio quantity changes, reconciliation decisions, or execution gating. The route described in [Kite settlement readiness diagnostics](kite-settlement-diagnostic-report.md) does not invoke it with holdings/positions data. This adapter is not evidence that a live Kite account was queried or that settlement occurred.

## Required provenance

The first `prepare` argument is the numeric StoX profile ID. The second is the exact string Kite `broker_user_id`; these identities are never interchangeable. A candidate snapshot needs `provider: kite`, that exact `broker_user_id`, a capture instant, and a structured `source_proof` receipt containing Kite provider, the same broker user ID and capture instant, a bounded capture ID, and successful requested `holdings` and `positions` source results. The receipt is caller-supplied and shape-checked, not cryptographic proof or a live authentication step. The adapter emits no signed account identity or broker-validation assertion. Its completeness flags mean only that the supplied receipt and row shapes passed local checks; they do not establish that Kite returned the data or authenticated the account. Missing, wrong-provider, mismatched, incomplete, or out-of-scope source data cannot establish completeness.

Snapshots require bounded list-shaped holdings and both net and day position buckets. An explicit empty list is meaningful only when it came from a verified source capture. Each identity and quantity is validated. Holdings require finite positive quantities and finite nonnegative T1/used quantities. Position quantities must be finite and bounded. Symbols, exchanges and supplied ISINs are pattern checked. Cash is always non-comparable.

Each candidate persisted import must carry the current numeric `profile_id` and exact string `broker_user_id`. The durable CNC import table stores a nullable `broker_account_id`, not `broker_user_id`; legacy rows without account provenance are deliberately excluded and make trade evidence incomplete. A profile ownership relation alone does not establish which Kite account created a fill. The current diagnostic route also does not load or pass these candidate imports to this adapter.

## Historical coverage and dates

Trade completeness requires a separate coverage record with source `persisted_historical_imports`, explicit valid `from` and `through` dates, `complete: true`, `through` equal to the as-of date, and `active_account_broker_user_id` equal to the current account. A completed current-day Kite Trades request is not historical coverage and must not be supplied as such. Unknown gaps, unavailable active account identity, malformed records, and account switches leave trade evidence incomplete. Accepted trade statuses are `imported`, `matched_manual` and `matched_existing`; review-only or unresolved candidates do not qualify. Duplicate broker trade IDs make the batch incomplete, even when repeated content matches, so repeated observations are not silently accepted as additional evidence.

UTC or offset timestamps are parsed as instants and converted to `Asia/Kolkata` before assigning a session date. Settlement dates use `TradingCalendar::addSessions`; only dates recognized as sessions by that calendar are emitted. An execution on an unmodeled Saturday or other non-session date remains unresolved. Exceptional Saturday sessions require authoritative calendar support; this mapper does not invent them or settlement dates.

The row limit is 5,000. Invalid or oversized input fails closed. Positions stay in separate buckets and are never added to holdings. The adapter's output remains internal to the shadow comparator. No live Kite payload, broker settlement behavior, or account evidence is asserted.
