## Changes in this delivery

The existing UX003 implementation was present on the fetched master baseline. The audit identified that client-side request ordering protected one browser instance but did not prevent a stale dashboard definition from overwriting a newer save on another device. Named records now carry a monotonic revision. Definition updates must present the revision they loaded; the API locks the current row, rejects mismatches with HTTP 409 and increments revision after accepted writes. A follow-up review found that GET-time legacy normalization also writes definitions, so it now locks the account and scoped records in the same order as PUT. This prevents normalization from overwriting a concurrent save and makes a normalization revision visible to stale clients. PUT returns its transaction's captured model, avoiding a post-commit read that could make the client adopt a later writer's revision for an older local definition. Client record merges never replace a newer definition with a lower-revision response; sequential autosaves retain the exact accepted revision as their next precondition. Normalization comparison sorts object keys recursively but preserves list order, so MySQL JSON key canonicalization does not repeatedly advance an unchanged definition's revision. Regression coverage exercises reordered object keys. The migration adds the revision column to existing installations with a fresh revision of 1.
