## Decision summary

OPS001 is a material operations feature, not a documentation-only wrapper around an already-complete Admin workflow. The V8 engine supplies a useful foundation (bounded per-stock work, retries, provenance-aware fact storage, deterministic provider order and an operator command), but almost every OPS001 control-plane acceptance criterion is absent. The current Admin page operates the separate incremental freshness updater and manual spreadsheet import; it does not operate V8 historical bootstrap runs. There is no recurring bootstrap scheduler, queue-of-runs model, cancellation, warning/gap ledger, notification integration for bootstrap outcomes, or OPS001 export.

The primary implementation-start dependency is FEAT-054's explicitly open provider/deployed-runtime acceptance. The recorded PO policy makes Yahoo the primary source and NSE/BSE optional matching fallbacks; their disabled/unconfigured state alone is not a blocker. Yahoo historical statement retrieval is demonstrated for only three issuers and one bounded bootstrap; that does not establish adequate availability across the eligible universe, metric/cadence combinations or duration needed to close OPS001. Do not treat the inherited “IMPLEMENTED” labels as operational acceptance.

## Current capability and source evidence

### Existing V8 foundation

- `app/app/Services/Fundamentals/FundamentalBootstrapService.php`: creates a run and per-stock jobs transactionally; rejects empty/unmatched explicit stock targets; processes bounded slices (max 100) under a cache lock; retries with persisted backoff; excludes benchmark instruments; writes through `FundamentalHistoricalIngestService`, `FundamentalDataService` and anomaly guard; stores row counts/coverage and normalized run summary. This is an engine, not an OPS001 run manager. The lock is slice-level; the service has no queue scheduler or explicit cancellation state.
- `app/app/Models/V7/FundamentalBootstrapRun.php`, `FundamentalBootstrapJob.php` and migrations `2026_09_27_140001_create_stox_fundamental_bootstrap_tables.php`, `2026_10_03_100002_add_fundamental_bootstrap_retry_schedule.php`: durable run/job lifecycle and retry fields exist. Run fields do not capture immutable scope/configuration, preset/schedule version, date/metric/cadence bounds, initiating trigger taxonomy, or cancel state. Jobs are unique by `(run_id, stock_id)`, not by metric/period.
- `app/routes/console.php` registers `stox:fundamentals-bootstrap` for manual `--all`, symbol targets, failed/partial reruns and a selected run slice. It is explicitly described as a manual operator action. `.github/workflows/run-fundamentals-bootstrap.yml` and `app/deploy/scripts/stoxla-run-fundamentals-bootstrap.sh` provide a controlled full bootstrap invocation, but neither is a durable recurring Admin scheduler or end-user run queue.
- `app/routes/api.php` Admin group exposes `/admin/fundamentals`, settings, manual workbook import, incremental update runs/process, and bootstrap status. It has no historical bootstrap create/control/history endpoints. Existing `EnsureUserIsAdmin` middleware is the reusable authorization boundary.
- `app/resources/js/src/pages/FundamentalDataAdminPage.jsx` presents update settings, an incremental “Run slice”, exchange fallback configuration and version 2.1 spreadsheet upload. It does not show historical bootstrap runs/jobs or OPS001 controls.
- `app/app/Services/Fundamentals/FundamentalDataService.php` retains revision/source logic and selects Yahoo first, consulting a matching exchange historical source only if Yahoo yields no usable rows (`docs/audit/V8-FEAT-054-ACCEPTANCE-AUDIT.md`, requirement matrix). OPS001 must reuse this policy; no Admin source override is permitted.
- Cadences supported by the historical engine are **quarterly and annual** (`FundamentalBootstrapService::bootstrapStock`). The engine fetches statement rows for those two cadences; there is no metric-specific or date-bounded run selector demonstrated. The canonical metric catalogue is `app/config/fundamentals_catalog.php` and `app/app/Services/Fundamentals/FundamentalMetricCatalog.php`; persisted metrics are not equivalent to provider availability. Existing completeness evidence counts canonical fields but the audit excludes 15 PO-approved exception fields from its field threshold.

### Manual Excel fallback

An implemented manual import exists, but it is not a substitute for the frozen Admin operations workflow. `docs/current/MANUAL-FUNDAMENTALS-XLSX-IMPORT.md`, `ManualFundamentalSpreadsheetImporter.php`, and `FundamentalManualSpreadsheetImportTest.php` define version 2.1 `.xlsx`; only the “Data Sheet” tab is read. It accepts standalone/consolidated basis, hashes the workbook, records uploader/name/version/basis and uses upload date as conservative availability because the template lacks publication dates. Re-upload is deduped/revisioned by normal fact storage. Controller restricts upload to Admin route, active non-benchmark symbol/exchange, 5 MB, `.xlsx`, and explicit company confirmation.

This checkout contains no real `.xlsx` sample/template artifact; tests create a synthetic minimal workbook fixture. Therefore real-world template sample compatibility, issuer naming/period conventions and manual fallback coverage are unverified. Before implementation acceptance, obtain a non-sensitive representative workbook sample and expected normalized rows for at least one quarterly/annual case, including sparse/missing rows and a changed value; do not place issuer-private or licensed data in the repository without approval.

### Resolved from frozen decisions and local implementation

- **OPS001 scope and source policy — resolved.** The frozen OPS001 spec says date bounds, cadence-specific runs and metric-specific runs are supported only “where supported.” Current `FundamentalBootstrapService` resolves stock targets and fetches complete quarterly and annual historical statement bundles; it has no metric/date selector, and job identity is `(run_id, stock_id)`. Therefore keep both quarterly and annual as the supported bootstrap cadences, keep metric/date targeting out of acceptance/UI promises, and reject unsupported combinations. No new Product Owner decision is needed unless product later requests those selectors.
- **Cadence and metric denominator — resolved.** The engine cadences are quarterly and annual. The 40 canonical primary facts are `revenue`, `operating_profit`, `ebit`, `ebitda`, `net_income`, `eps`, `eps_diluted`, `interest_income`, `interest_expense`, `net_interest_income`, `total_assets`, `total_liabilities`, `equity`, `debt`, `long_term_debt`, `cash_and_equivalents`, `trade_receivables`, `inventory`, `current_assets`, `current_liabilities`, `property_plant_equipment`, `capital_work_in_progress`, `gross_npa`, `gross_npa_ratio`, `net_npa`, `net_npa_ratio`, `capital_adequacy_ratio`, `provisions`, `net_interest_margin`, `operating_cash_flow`, `investing_cash_flow`, `financing_cash_flow`, `capital_expenditure`, `dividends_paid`, `shares_outstanding`, `promoter_holding`, `fii_holding`, `dii_holding`, `public_holding`, and `promoter_pledge`. The FEAT-054 gate is at least one value and 50% coverage among covered stocks for each non-exempt primary fact. - **Provider fallback scope — resolved.** The recorded PO decision is Yahoo primary; matching NSE/BSE data is consulted only if Yahoo has no usable rows. The frozen OPS001 spec requires existing deterministic source rules, not that optional official fallback adapters be enabled. Thus their disabled/unconfigured state is not an independent OPS001 prerequisite and no extra licensing gate is introduced here. FEAT-054 remains open on broader Yahoo deployed availability/coverage and on proving fallback behavior when such source is configured/authorized; this needs bounded existing authorization/configuration or a documented reason that no canary is permitted.
- **Writer/lock ownership map — design resolved; runtime/test proof remains.** `FundamentalBootstrapService::PROCESS_LOCK_KEY` is `stox:fundamentals:bootstrap-process` (Cache lock, 900-second lease per processing slice). `FundamentalUpdateService` uses separate `stox:fundamentals:process-slice` and `stox:fundamentals:scheduled-slice` Cache locks, also 900 seconds. They do not form a shared whole-run exclusion lock. Both paths write through `FundamentalDataService`, which uses a MySQL transaction, locks the parent `stocks` row, then locks matching current facts before revision/upsert. That per-stock DB transaction is the actual shared fact-writer serialization point; lock ordering/uniqueness and expiration behavior still require isolated MySQL interleaving tests. OPS001's one-active-run invariant must be its own durable run/claim protocol and must not replace these writer locks. DATA003 owns forward polling/provider-check freshness; OPS001 owns historical runs. No deployed lock store/key owner or lease state has been independently observed.
- **Supported concurrency exit check — concrete.** On isolated MySQL, interleave bootstrap and incremental update for the same stock/cadence, including a worker stalled beyond its cache lease. Verify a single valid current fact, retained prior revision/provenance, deterministic run/job counts and no stale claimant finalizing another claim. Separately verify OPS001's durable one-active-run claim. Do not manipulate production locks or induce races there.
