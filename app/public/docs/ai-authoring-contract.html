AI Authoring Contract (Normative Rules)

ai-authoring-contract · screen: /docs/ai-authoring-contract.html

RFC 2119 constitution for authoring portable Trading Artifacts. Read this first; other guide sections are detailed reference.

Overview

This Contract is the constitution of Trading Artifact authoring.

Keywords follow RFC 2119: MUST, MUST NOT, SHOULD, SHOULD NOT, MAY.

Detailed schemas, catalogues, runtime maths, and JSON samples live in later sections. Do not invent behaviour absent from this Contract and those references.

Maintenance rule: Any new authoring or behavioural constraint MUST be added here before it is documented elsewhere in this guide.

General Principles

  1. AI MUST generate portable Trading Artifacts (JSON envelopes) consumable by Validate / Import.
  2. AI MUST rely only on functionality documented in this guide.
  3. AI MUST NOT invent undocumented features, operators, indicator ids, parameter names, or optional sections.
  4. AI MUST prefer canonical registry identifiers over aliases.
  5. AI MUST NOT read or depend on application source code to author artifacts.
  6. AI SHOULD minimise unnecessary configuration.
  7. AI SHOULD produce human-readable name and slug values.
  8. AI SHOULD treat later guide sections as reference manuals subordinate to this Contract.

Artifact Envelope

  1. Every artifact MUST include schema_version.
  2. schema_version MUST equal "1.0" for artifacts authored against this guide.
  3. Every artifact MUST include artifact_type matching the payload (indicator | screener | strategy).
  4. Artifact body fields MUST use the portable key definition (not database column names such as definition_json or config_json).
  5. Every artifact MUST include slug.
  6. Every artifact MUST include name.
  7. Every artifact MUST include metadata as an object (empty object allowed).
  8. Unknown top-level envelope fields SHOULD NOT be introduced.
  9. minimum_engine_version MAY be included; it is exported for documentation and is not currently enforced on Validate/Import. See Runtime Semantics.
  10. AI MUST NOT place Screener condition trees or Strategy scoring rows outside definition.

Indicator Rules

  1. Screeners MUST use only screenable Primary indicator ids from the Indicator Registry.
  2. Strategies MUST use only strategy-scorable Composite keys in scoring_model.
  3. No indicator id MUST be treated as both screenable and strategy-scorable.
  4. Indicator ids MUST exactly match the Indicator Registry (canonical spelling).
  5. Parameter names MUST exactly match the Indicator Registry for that indicator.
  6. Unknown indicator ids MUST NOT be invented.
  7. Unknown parameter names MUST NOT be invented.
  8. Parameter values that are present MUST be numeric where the registry requires numbers.
  9. Parameter values that are present MUST lie within catalogue min/max for that parameter.
  10. Out-of-range parameter values MUST NOT be authored (Validate rejects; values are not clamped).
  11. Screener params keys MAY be omitted; omitted keys resolve via TechnicalIndicatorService fallbacks. See Runtime Semantics / Indicator Registry.
  12. AI SHOULD set Screener params explicitly so runtime values match author intent (catalogue UI defaults may differ from runtime fallbacks).
  13. AI SHOULD NOT invent Indicator Registry shipping calculators; Indicator create/update drafts do not mutate release calculators.

Screener Rules

  1. Every Screener MUST contain definition.root.
  2. root MUST be a group or condition node.
  3. Every Screener MUST contain at least one condition somewhere under root.
  4. Group operators MUST be exactly AND or OR.
  5. Condition operators MUST be exactly one of: gt, gte, lt, lte, eq.
  6. Unsupported operators MUST NOT be used (neq, NOT, crosses_above, crosses_below, between, outside, contains, in, and similar).
  7. Each of left and right MUST be either an indicator operand or a constant operand.
  8. Constant operands MUST use { "type": "constant", "value": <number> }.
  9. Constant values MUST be numeric.
  10. Boolean operands MUST NOT be used.
  11. String operands MUST NOT be used.
  12. Null and date operands MUST NOT be used.
  13. Indicator operands MUST use { "indicator": "<id>", "params": { ... } } shape (params object MAY be empty or omit keys per rules 29–30).
  14. Nesting depth MUST NOT exceed 4.
  15. Condition count MUST NOT exceed 40.
  16. eq MUST be treated as float equality with documented epsilon; prefer gte/lte for thresholds. See Runtime Semantics.
  17. AI SHOULD express “between” as AND of gte and lte.
  18. AI SHOULD express “outside” as OR of lt and gt.
  19. Screener slug MUST be unique within the target portfolio (Import may suffix on collision).

Strategy Rules

  1. Strategies MUST reference Screeners via screener_slug and/or screener_factory_key in eligibility_sources.
  2. Strategies MUST NOT embed Screener trees (definition.root, nested condition groups) inside Strategy JSON. See Strategy Registry.
  3. definition.scoring_model MUST be present (alias indicators is accepted and normalised).
  4. scoring_model MUST contain at least one enabled row with weight > 0.
  5. Enabled scoring weights MUST total exactly 100 (±0.01).
  6. Only strategy-scorable Composite keys MAY appear as scoring key values.
  7. Unknown scoring keys MUST NOT be used.
  8. Scoring row enabled: false MUST be treated as excluded from weight totals and contributions. See Runtime Semantics.
  9. When both minimum and maximum are set on a scoring row, the pass band MUST be interpreted as minimum <= value <= maximum.
  10. Failing a scoring minimum or maximum MUST NOT reject the stock from Recommendations; contribution is zero and weight still dilutes overall. See Runtime Semantics.
  11. Multiple eligibility_sources MUST be interpreted as UNION of candidates (not intersection).
  12. priority on eligibility sources MUST be treated as sort order only.
  13. Optional sections thresholds, portfolio_rules, exit_strategy, and market_gates MAY be included when documented in Strategy Registry.
  14. AI MUST NOT invent undocumented Strategy definition sections or exit rule keys.
  15. Exit rule keys MUST be chosen from the documented set (ma_breakdown, rs_weakening, trend_weakening, score_exit, max_loss, atr_stop, trailing_stop, screener_exit).
  16. exit_strategy.mode MUST be any or all when present.
  17. AI SHOULD Export an existing Strategy before large edits to preserve thresholds, exits, and gates.

Runtime Behaviour Rules (Authoring-Relevant)

  1. AI MUST NOT assume failing one scoring factor hard-rejects the candidate. See Runtime Semantics §1.
  2. AI MUST NOT assume eligibility INTERSECTION when multiple Screeners are listed. See Runtime Semantics §3.
  3. AI MUST NOT assume minimum_overall_score is a hard Recommendation pipeline gate. See Runtime Semantics §4.
  4. AI SHOULD assume market gates demote OPEN/INCREASE only and still allow EXIT/REDUCE. See Runtime Semantics §6.
  5. AI SHOULD assume insufficient cash can demote OPEN/INCREASE to WATCH. See Runtime Semantics §7.
  6. AI MUST NOT embed exit logic as Screener trees inside Strategy; use documented exit rule keys or screener_exit references.

Import Rules

  1. JSON MUST be Validated successfully before Import.
  2. Import MUST NOT be performed on invalid or unvalidated JSON.
  3. AI SHOULD Validate after every material edit.
  4. AI SHOULD Import Screener before Strategy when the Strategy references that Screener by slug.
  5. Strategy Import MUST be treated as creating a draft until Select activates it.
  6. AI SHOULD prefer Export → edit → Validate → Import over authoring large optional sections from scratch.
  7. AI SHOULD expect Import normalisation (aliases, weight redistribution, slug/name collision handling). See Runtime Semantics §12.
  8. AI MUST NOT rely on unknown top-level Strategy definition keys surviving Import.

Validation Rules

  1. Validation errors MUST be resolved before Import.
  2. Invalid JSON MUST NOT be imported.
  3. Validation MUST precede every Import attempt.
  4. AI MUST treat Validate ok as the sole gate that enables Import in Registry UI.
  5. Editing JSON after Validate MUST be assumed to clear validation state.

Portability Rules

  1. JSON MUST remain portable across portfolios.
  2. JSON MUST NOT depend on local database primary keys for cross-portfolio portability.
  3. screener_slug or screener_factory_key SHOULD be preferred over screener_id in authored Strategy eligibility.
  4. AI SHOULD declare dependencies when the envelope format includes them.
  5. AI MUST NOT hard-code portfolio-specific absolute paths or environment secrets into artifacts.

AI Authoring Best Practices

  1. AI SHOULD prefer canonical indicator and scoring ids.
  2. AI SHOULD NOT invent registry ids.
  3. AI SHOULD NOT invent operators.
  4. AI SHOULD NOT invent optional Strategy sections beyond those documented.
  5. AI SHOULD omit Screener parameters only when the intended runtime fallback is known and acceptable.
  6. AI SHOULD preserve existing metadata when editing an Exported artifact.
  7. AI SHOULD generate distinct, descriptive name strings.
  8. AI SHOULD use Trading Cookbook recipes when matching a documented investing style.
  9. AI SHOULD note Cookbook approximations (for example Value without PE, Darvas/CANSLIM proxies) in metadata or names when relevant.
  10. AI SHOULD keep one atomic concern per Screener where practical.
  11. AI SHOULD keep Strategy scoring rows aligned to Evaluation composites the engine actually emits.

Pre-Generation Checklist

Before emitting JSON, AI MUST verify:

  • schema_version present and equal to "1.0"
  • artifact_type correct (screener or strategy)
  • slug, name, metadata, and definition present
  • Field name is definition (not DB column names)
  • Indicator ids exist in Indicator Registry for the intended use (screenable vs scorable)
  • Parameter names match the registry; present values within min/max
  • Screener operators are only gt/gte/lt/lte/eq and groups only AND/OR
  • Operands are indicator or numeric constant only
  • Nesting depth ≤ 4 and condition count ≤ 40
  • Strategy has no embedded Screener trees
  • Eligibility uses screener_slug / screener_factory_key
  • Enabled scoring_model weights total exactly 100
  • Scoring keys are strategy-scorable only
  • Optional sections/keys are documented only
  • JSON is portable (no reliance on local DB ids)
  • Validate → Import sequence planned (Strategy remains draft until Select)

Practical tip: treat this page as one step in a larger workflow, not an isolated screen. Make one change at a time, verify the downstream effect, and use linked pages to complete the loop (for example: discovery → evaluation → recommendation → pending execution → review).
